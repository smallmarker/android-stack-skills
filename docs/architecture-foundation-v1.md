# Architecture Foundation v1

状态：设计提案。现行行为与验证证据见[成熟度审查和实施路线图](architecture-audit-v1.md)，首个具体模式见 [Network Architecture v1](network-architecture-v1.md)。

Android Stack Skills 的产品承诺是给出可追溯的架构决策、可采用的最小实现以及有边界的验证证据。Agent 负责理解业务和实施变更。Recipe 提供参考实现，Inspector、Resolver、Installer 负责识别和安全交付，Validator 提供构建和测试证据。架构符合性由实际业务路径的证据和审查共同判定。版本号属于架构文档，与 CLI、Recipe 版本分别记录。

## 决策顺序

先选目标模块和一条真实业务路径，读取现有分层、构建依赖、DI 根、数据所有者和测试。用业务变化和团队边界判断复杂度；页面数和代码行数只作线索。既有应用沿用已验证的决策，局部新增规则先在本次改动的路径内落地。

| 决策 | 默认与升级条件 | 应记录的证据 |
| --- | --- | --- |
| 单模块或多模块 | 新项目先单模块，以包区分职责。存在独立团队维护、可复用能力、真实构建瓶颈或需要编译期隔离时，拆第一个边界。先测量构建成本，再判断构建速度能否成为拆分理由。 | 模块图、所有者和拆分收益 |
| UI 状态与 MVVM | 简单展示和控件临时状态可留在组件。异步业务状态、跨重建保留或需要独立测试时，用屏幕级 ViewModel、只读状态流和显式动作。需要组合保留内容与刷新状态时用不可变数据类，需要互斥时用 sealed 状态。 | 状态转移、重复触发策略、配置变化和进程死亡要求 |
| Repository | 业务数据默认经一个数据入口，即使只有单一来源。单来源可用具体 Repository 直接依赖 Service。出现缓存、离线同步或多源时，Repository 拥有数据来源协调与一致性策略。纯静态界面可直接渲染。 | 数据所有者、事实来源、刷新和失效语义 |
| Repository 接口 | 默认具体类加构造注入。真实替代实现、跨模块稳定契约，或缺少更小的行为测试接缝时才抽接口。已有接口按既有契约维护。 | 替换方或测试所需的接缝 |
| Domain | 跨屏共享、多个数据入口编排、或独立复杂业务规则出现时按用例增加。单一转发保持在原路径。业务模型可位于 data 的公开边界，无需独立 Domain 模块。 | 被复用或独立演进的规则 |
| DI | 在 Application 或应用装配根用构造注入并显式管理实例范围，按需使用 ViewModel Factory。已有 Hilt 保留。当对象图、作用域和测试替换的成本显著增加时选 Hilt。 | 谁创建与销毁依赖，测试如何替换 |
| 错误与并发 | 先用项目现有的类型化结果或明确的异常契约，已知失败转换为业务和 UI 可处理状态。读取可选 latest-wins 或合并，写入应明确拒绝重复、串行或按键去重。 | 失败类别、取消所有者、竞争顺序、重试和重复写入影响 |
| 可测试性 | 把测试接缝放到依赖变化的位置，用构造注入、控制的时间和明确状态验证行为。 | 能用假依赖验证业务，能用真实适配器验证协议 |

例：单团队新闻客户端可用一个模块、屏幕 ViewModel、具体 Repository 和 Service，列表刷新选择 latest-wins。已有 Hilt 的多模块订单 App 保留模块与装配约定，共享订单规则可以抽用例；提交订单只有后端确认去重语义后才允许自动重放。旧工程存在 UI 直连 Retrofit 时，新订单路径先建立数据入口，并记录仍待迁移的旧调用点。

## 跨 Skill 契约

### 必须遵守的不变量

| ID | 约束 | 责任方 |
| --- | --- | --- |
| C1 | UI 只依赖业务数据入口或用例。数据层可依赖内部网络、持久化适配器。适配器与业务数据层不得依赖 UI。应用装配根可引用具体实现。Gradle 模块依赖无环，跨模块只暴露使用者需要的 API。 | Project、各能力 Skill |
| C2 | DTO、HTTP 类型、数据库实体留在适配或数据实现边界。UI 依赖稳定应用模型和呈现状态，UI 的格式化文字和资源不进数据层。图片引用可作为应用模型，图片请求对象与 View 生命周期归 UI 适配器。 | Project、Network、Image |
| C3 | 在拥有语义的边界处理预期失败。传输失败、业务拒绝与程序错误有独立语义。UI 使用安全、可本地化的错误描述。取消向调用者传播，禁止转成失败 UI、成功、重试或登出。 | Project、Network |
| C4 | suspend/Flow 的工作默认归调用者。明确生命周期、重复动作和过期响应处理。API 应 main-safe，阻塞 I/O 由执行者切到 IO，重计算用 Default，UI 操作在 Main。可控 Dispatcher 或调度器由边界注入；已 main-safe 的 Retrofit suspend 无需统一套 IO。跨屏或跨进程的任务必须由显式应用范围或持久调度器拥有。 | Project、Network、Image |
| C5 | 凭据仅进授权边界，生产业务网络使用 HTTPS，保留系统证书校验；避免硬编码真实凭据和敏感 URL。图片如含私有数据，明确图片客户端、凭据范围和缓存/登出策略。 | Network、Image |
| C6 | 只记录经评审的静态事件名、标签和字段来源，禁止原始正文、Token、Cookie、敏感 URL 和异常消息。默认关闭网络正文日志和 release 调试输出。记录失败的组件应明确，避免重复记录或把取消当故障。 | Logging、Network、全体调用方 |
| C7 | 每个新边界至少有一条真实行为证据，对变更涉及的失败、取消、安全或生命周期加回归。已有项目保留工具链和成熟实现，升级单独验证，行为或契约变化记录迁移及回滚。未验证组合要标明范围。 | 全体 Skill |

### 规模选项与框架约束

- 规模选项包括包或模块隔离、独立 Domain、Repository 接口、Hilt、离线协调和应用级任务。将触发条件写入项目决策，避免随模板机械引入。
- Compose 屏幕生命周期感知收集状态，XML 用 `repeatOnLifecycle`，Fragment 绑定 view 生命周期。ViewModel 不持有 View、Activity 或生命周期对象。对进程死亡有要求的状态明确区分可恢复参数和重新加载的数据。
- Retrofit DTO、注解和 Gson 映射集中在数据实现。OkHttp client 按 origin 和策略复用，重放规则需验证。Coil 使用已有 loader，Glide 在主线程绑定 View 并按复用/释放清理；真实列表要验证性能。Timber 通过受约束的 facade，Application 以应用构建变体初始化一次。具体约束随所选实现进入评审。

## 验证与验收

| 范围 | 可自动验证 | 需要人工或 Agent 审查 |
| --- | --- | --- |
| C1/C2 依赖与模型 | 用已有静态检查或项目测试约束已知模块图和包的禁止依赖，审查 public API 类型；规则可用违例样本证明能失败。单模块 import 扫描只能作线索。 | 语义泄漏、类型别名或间接绕行、例外和装配根的位置 |
| C3/C4 行为 | 可控调度下测试成功、失败、取消、重入和过期结果。真实网络夹具测在途取消及 HTTP 分支。对需要的 UI 路径做设备或 UI 测试。 | scope 所有权、线程负荷、事件消费和状态可恢复性是否符合业务 |
| C5/C6 安全 | 双 origin 请求断言、release 捕获测试、日志注入秘密哨兵及禁止调用扫描。 | 动态 URL、日志字段来源、私有图缓存、绕过 facade 的 SDK 和代码 |
| C7 与维护成本 | 选定模块的 Gradle 构建、测试、实际依赖解析和必要的 release/设备检查，记录版本和夹具。 | 抽象收益、职责是否清晰、后端契约是否真实、升级和回滚是否可行 |

验证结果按规则记录为通过、失败、未覆盖或不适用，并附命令、版本、测试路径或审查依据。构建通过只证明该次构建与执行的测试通过。架构审查记录应能指出一条调用链、它的错误出口和取消所有者。发现旧问题，记录范围和后续动作。新增路径的安全、取消或重复写入缺陷应先修再验收。

## 后续业务开发

沿用目标项目的 README 或 ADR 作为决策来源，推荐一份短的 `docs/architecture.md`；已有同义文档时直接补充。根 AGENTS.md 如已使用，可增加指针。记录 Foundation 版本、目标模块与依赖方向、现有 DI/数据入口、状态和错误模式、重放/日志策略、验证命令与已知例外。既有项目无记录时，从一条已工作的调用链建立初始决策，标出尚未核实的事项。Recipe 的 Usage.md 给出实现入口，安装 manifest 仅用于判断文件所有权和版本。已安装的 Recipe 示例可用于阅读。新增 Service、DTO、Repository 和测试写在应用自有路径，引用可复用的客户端设施，避免把业务代码写进 hash 管理文件。确需改变已有示例时，审查影响并记录显式迁移。下一轮将最小工作流写入现有 SKILL.md 和生成 Usage.md，使已安装的 Skill 即使无法打开上游完整文档，也能找到项目决策和验证入口。

每次开发时，Agent 先读项目决策和相关 Skill/Usage，追踪同类调用链，再列出本次涉及的契约 ID。沿现有边界写代码并补行为验证。需要改变选定模式时同步更新项目决策与迁移范围。安装和环境准备沿现有流程执行。业务增量通常由现有编辑和 Gradle 路径完成。

| 后续任务 | 必查与验证 |
| --- | --- |
| 新增业务 API / Repository 方法 | 从已确认的后端契约定义 DTO 和错误，复用数据入口，核对结果类型、请求重放和取消；验证映射与 HTTP 行为 |
| 新增 ViewModel 状态 | 明确动作、所有者与重复触发行为，测试状态序列、取消与竞态 |
| 新增错误处理或修改鉴权 | 检查 UI 文案、旧调用者、来源隔离、并发刷新、日志与业务重放，补对应分支 |
| 升级 Retrofit | 查看锁定版本和解析图，按[网络升级门禁](network-architecture-v1.md#升级与替换)验证 |
| 检查旧代码 | 从入口追踪一条调用链，按 C1–C7 给出路径、证据、影响和最小修复，分开报告已有问题和本次回归 |
